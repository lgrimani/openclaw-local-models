# OpenClaw agent-DB integrity gate: `no-proof` / slow opens / dropped turns

**Status:** resolved 2026-11-06 by upgrading to OpenClaw **2026.11.1**.
**Symptoms:** replies die with `⚠️ OpenClaw couldn't finish this request`; cron jobs fail with
`SQLite worker stopped before its result was received: Error: disk I/O error` /
`SQLite settlement failed: Error: Session metadata domain is closed`; every turn feels slow.

If you are seeing these, read this before trying anything else. Much of the obvious advice is wrong.

---

## Quick diagnosis (5 minutes, read-only)

1. **Installed version** — read it live, never from memory or an earlier session:
   ```bash
   node -p "require('$(npm root -g)/openclaw/package.json').version"
   ```
2. **Is the gateway on that build?**
   ```bash
   systemctl --user show openclaw-gateway -p MainPID -p ExecMainStartTimestamp -p NRestarts
   ```
3. **Clean-close receipts** — the single most informative signal:
   ```bash
   journalctl --user -u openclaw-gateway --since today --no-pager | grep -i "clean-close receipt"
   ```
   - `written` → healthy, stop here.
   - `read-only` / `active-leases` → the seal is not publishing; you have the bug.
4. **Slow opens** (should be zero):
   ```bash
   journalctl --user -u openclaw-gateway --since today --no-pager | grep -c "slow OpenClaw agent database open"
   ```
   Look at `integrityGateReason=`, `integrityGateMode=`, `elapsedMs=`. `no-proof` + `full` + 6–9 s = the bug.
5. **Fatal errors:**
   ```bash
   journalctl --user -u openclaw-gateway --since today --no-pager | grep -ci "disk I/O error\|domain is closed"
   ```
6. **Leases and seals** (safe to read live from the state dir; `sqlite3` on the *agent* DB is refused by design):
   ```bash
   cd ~/.openclaw/state
   sqlite3 openclaw.sqlite  "select lease_id, owner_pid, datetime(opened_at/1000,'unixepoch','+8 hours') from agent_database_leases;"
   sqlite3 openclaw-quarantine.sqlite "select path, app_version, clean_close, datetime(verified_at/1000,'unixepoch','+8 hours') from agent_integrity_verifications;"
   ```
   - More than one lease row for the same pid+path = defect.
   - `clean_close = 0` on the agent path = the gate can never skip the full check.

---

## Root cause

On 2026.10.9 the close path did **not** publish a clean-close seal:

```js
// 2026.10.9
else receipt = markOpenClawAgentIntegrityClean(...)
// 2026.11.1
else receipt = closeOutcome.publishSeal() ? "written" : "verification-missing";
```

Without a seal, `readOpenClawAgentIntegrityVerification` finds nothing, the gate resolves to
`integrityGateReason=no-proof` with `integrityGateMode=full`, and **every** DB open pays a full
`PRAGMA integrity_check`. Reply admission waits on that open
(`reply.admit_pre_dispatch: 8047ms` of an 8120 ms reply), so turns exceed their window and die.

Two contributing defects, neither sufficient alone:
- Duplicate lease rows per pid+path — `claimAgentDatabaseLeaseInDatabase` deletes only *stale*
  rows, then inserts a fresh `randomUUID()` unconditionally; no dedupe on `(agent_id, path, owner_pid)`.
- `recordOpenClawAgentIntegrityVerification` writes `clean_close: 0` on every open, so the proof
  is consumed rather than persisted.

Upstream: `openclaw/openclaw#186631` (the exact `active-leases` / `no-proof` pair), `#173440`,
`#161403`; PRs `#155785`, `#182984`, `#159445`.

---

## The fix

**Upgrade to 2026.11.1 or later.** That is the whole fix. Nothing else was required.

Verified after restart, all five on 2026-11-06:
- one lease row for one pid (was two)
- `clean_close = 1` in `openclaw-quarantine.sqlite` (was pinned at 0)
- zero `slow OpenClaw agent database open` lines (was dozens/hour at 6–9 s)
- zero `disk I/O error` / `domain is closed`
- WAL 923 KB on a 286 MB DB (was 14–40 MB)

## Dead ends — do not repeat these

| Attempt | Why it fails |
|---|---|
| Trimming / `VACUUM` the agent DB | 280 MB is not large. A bare `integrity_check` on ~280 MB measures 0.35–2.5 s warm/cold. The 6–9 s is writer blocking around the check, not the check. |
| Stop → delete lease rows → checkpoint → start | The gateway re-mints leases within seconds of start. Also, per `#173440`, `clean_close` cannot become 1 "while the gateway holds the DB open" on an affected build. |
| Killing processes holding the DB | `openclaw` with no args attached to a socket at `127.0.0.1:18789` and holding **no DB file handles** is a **TUI client**, not a second gateway. Check `/proc/<pid>/fd` and `ss -tnp` before killing anything. |
| Deleting `-wal`/`-shm` | The WAL is regenerated by normal writes in `wal` journal mode; a large WAL is a symptom of checkpoint starvation, not the cause. |
| Reading the agent DB with `sqlite3` | Blocked by design under the active state dir. Use `ls -l` for sizes and `openclaw-quarantine.sqlite` for seals/leases. |

## Reporting a "resolved" verdict

Do not call it fixed from a pid change, a receipt line alone, or an earlier session's claim about
the installed version. Require: live version read, `clean-close receipt: written`, `clean_close = 1`,
zero slow opens, zero `disk I/O error`. Note that a seal row may legitimately carry the *previous*
version string if it was written before the restart — the seal value is what matters.
